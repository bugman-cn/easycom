# easycom 在线升级设计

已接入“关于 → 检查更新”。目标平台是 Windows，更新源为 easycom 公开 GitHub 仓库的 Releases。任何使用者都可以匿名检查和下载正式版，发布新版需要仓库发布权限。仓库地址在打包时确定，因此可以先开发并用本地测试包验证，再创建仓库。

## 用户如何升级

在主窗口的 **关于 → 检查更新** 手动查询。发现新版时显示当前版本、目标版本、发布说明和下载大小，提供 **下载更新** 和 **稍后**。下载与校验在后台完成，完成后才显示 **更新并重启**。

串口打开、正在连接或正在定时发送时，可以先下载，界面提示用户结束当前会话再安装。点击重启时重新检查状态，走主窗口已有的正常退出流程，等待串口线程退出、历史记录保存、接收队列和日志写完。下载失败或取消时，当前会话可以继续使用。

## 发布包约定

保留当前两种 PyInstaller 构建方式。下面用 V1.1 和 Windows x64 举例，实际版本取自 `APP_VERSION`，架构取自构建环境。

| 项目 | 约定 |
| --- | --- |
| Release 标签 | `v1.1`，对应已推送的 V1.1 源码提交 |
| 目录版附件 | `easycom-v1.1-win64.zip`，包内顶层为 `easycom.exe` 和完整的 `_internal/` |
| 单文件版附件 | `easycom-v1.1-win64-onefile.zip`，包内顶层为 `easycom.exe` |
| 随包许可 | 两种 ZIP 均在 EXE 旁附带 `LICENSE`、`THIRD_PARTY_NOTICES.md` 和 `licenses/`。更新时逐个替换新版随附的许可文件。 |
| 安装位置 | 两种方式均使用固定文件名 `easycom.exe`。版本号放在 Release 和附件名中，快捷方式继续指向同一路径 |

发布脚本按架构和模式生成独立 ZIP，程序内置更新源、架构和模式。更新源默认为 `bugman-cn/easycom`，构建时可以通过 `--update-repo OWNER/REPO` 指定。

## 检查、下载与校验

1. Windows 客户端通过 HTTPS 访问公开的 `https://github.com/OWNER/REPO/releases/latest`，按 GitHub 重定向的正式标签读取版本和发布说明。若页面结构无法识别，回退到 REST API。用户无需 GitHub 账号、CLI 或令牌。将正式标签中的两段或三段版本号按整数比较，例如 `v1.1` 等于 `v1.1.0`，`v1.10` 高于 `v1.9`。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
2. 公开页面查询不消耗 REST API 的匿名配额。备用 REST 查询的主限额是每个出口 IP 每小时 60 次。重新打开窗口时可复用 60 秒内的成功结果，点击检查按钮可立即刷新。若 GitHub 明确要求等待，则按响应头指定的时间暂停重试。遇到 404 时提示检查仓库地址和是否已发布正式版，网络错误可稍后重试。[GitHub 请求限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
3. 按当前模式和架构精确匹配一个 ZIP，从该附件所在行读取 GitHub 的 SHA-256，通过附件的 HEAD 响应读取准确字节数。网页未提供完整信息时，使用 REST API 的附件元数据。下载时只跟随受信任的 HTTPS 重定向，再核对字节数和 SHA-256。缺少摘要或校验失败时中止安装。摘要用于发现损坏或下载错包。[Release 附件元数据](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)
4. 在安装目录所在磁盘的临时目录解压。按表中的目录结构检查内容、入口 EXE 的版本以及磁盘空间，拒绝越界路径、链接和指向 `auto-gen/` 的条目。只有整个新版可用时才提示重启。源码运行可查看新版信息，自动安装面向打包版。

## Windows 文件替换与恢复

- **谁来替换。** 由当前安装包自带的独立更新助手执行，启动前将助手复制到待替换目录外。助手对当前安装目录加锁，在主程序正常退出且 EXE、DLL 解除占用后才动文件。另一实例仍在运行或退出超时时，提示重试。
- **替换范围。** 两种模式都替换 `easycom.exe` 和新版随附的许可文件，目录版还替换 `_internal/`。保留同级 `auto-gen/`、自定义日志和用户其他文件。更新前把旧程序文件移到同一磁盘的备份目录，逐步记录操作。更新过程只在当前用户可写的位置运行。
- **何时算成功。** 助手启动新版；新版完成配置读取、显示主窗口后，回传本次更新的启动确认。收到确认后才清理程序备份。复制失败或新版启动即崩溃时，助手恢复旧文件、重启旧版并保留错误记录。若新进程仍占用文件，先正常退出再恢复。断电中断时，从程序文件之外保留的恢复入口重放记录，继续恢复。首版沿用现有配置格式；以后若引入不兼容的数据迁移，需要单独备份受影响的配置。

## 实施顺序与验收

1. 先改 `scripts/release.ps1` 的产物名称和布局，用 V1.0、V1.1 测试包验证目录版和单文件版各自能正确选包。
2. 在 `gui/main_window.py` 的“关于”菜单接入更新界面，把 GitHub 查询、下载和校验放到后台。独立助手负责退出后的文件操作，沿用 `config/app_config.py` 现有的数据路径。
3. 用本地模拟 Release 验证两种模式的成功升级、重复点击、断网、限流、尚无正式版、摘要错误、串口忙、文件被占用、新版启动失败和中断恢复。核对 `auto-gen/` 中准备好的快捷命令、历史和日志，以及升级前建立的快捷方式。
4. 仓库创建并推送源码后，先打包并发布**包含更新入口的 V1.0**。发布 V1.1 后，在没有安装 GitHub CLI、没有登录 GitHub 的 Windows 环境中，从公开 Release 完成一次 V1.0 → V1.1 升级，核对配置、历史记录和快捷方式。此前已经分发的旧 EXE 需要手动换到带更新入口的版本一次。
